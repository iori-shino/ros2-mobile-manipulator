# Engineering log

This records observed problems in the project's Ubuntu/VMware simulation environment. A mechanism described as an observation or likely cause is not presented as a proven upstream defect. The evidence index is [VALIDATION.md](VALIDATION.md).

| Issue | Symptom → Root cause / evidence → Fix → Lesson |
|---|---|
| VMware rendering | Ogre2 shader errors or blank robot viewport; another hardware sensor path returned minimum LiDAR ranges → Renderer/virtual-GPU compatibility was implicated by backend comparisons; not a complete driver root-cause analysis → Use Ogre and Mesa software rendering on the Gazebo **server**, with a separate hardware-rendered GUI → Test visual rendering and simulated sensor data separately; rendering the GUI in software was not equivalent. |
| Four-wheel turn behavior | Wheels moved but skid-steer yaw/drift did not match the desired behavior → Turning needs lateral contact slip, and friction direction is evaluated in wheel collision coordinates → Keep the verified local `fdir1`, anisotropic `mu=0.2`, `mu2=0.8` and `slip1=0.035` → Ground-truth chassis pose is needed; wheel odometry alone cannot validate skid-steer motion. |
| Low real-time factor | The robot appeared much slower than its commanded speed → Simulation time advanced slower than wall time in the VM; one recorded 10 s sample gave RTF about 0.115 → Keep limits in physical/simulation units, explain time bases and use wall-clock safety timeouts → Do not compensate by increasing the robot's specified speed limit. This is an environment observation, not a fixed benchmark. |
| Control plugin path | ros2_control failed to load reliably with a bare plugin name → Library discovery depended on the environment's plugin search paths → Resolve the installed package prefix and pass its `libgz_ros2_control-system.so` path when generating the temporary model → Discover dependency paths at runtime instead of hard-coding a user's machine. |
| Gripper trajectory failures | Goal aborts or inability to complete requested jaw motion → Action result, actual joint state, limits and settling velocity must agree; multiple gripper experiments exposed interface/settling issues → Keep bounded targets, inspect action results, verify each jaw's physical state, and use the final validated controller settings → A published trajectory or accepted goal is not proof of physical completion. Exact causes of every early failed run were not retained and are not reconstructed as fact. |
| Lower-limit recovery | A prismatic jaw using the position interface could fail to reopen after reaching the lower stop → Repeatable behavior in this simulator/interface combination; upstream solver cause was not proven → Use effort/PID tracking without enlarging the original joint limits → Test recovery after contact with both limits, not only mid-range motion. |
| Velocity oscillation | High-damping gripper effort control oscillated at a 100 Hz update rate → Discrete control and physics interaction was sensitive to update rate → Use the verified 500 Hz controller manager and gains P=2000, I=100, D=20, integral clamp=1 → Gains and update rate form one configuration; ideal-simulation stability does not validate a real actuator. |
| Two-jaw synchronization | One scalar command was insufficient evidence that both jaws followed → URDF mimic alone was not the selected effort-hardware control path → Send equal position targets to both joints through the gripper trajectory controller and inspect both actual joint values → **The gripper still uses JointTrajectoryController.** Its command interface changed to effort; trajectory control was not removed. |
| Simulation time and TF | Apparent low topic rates, potential stale/duplicate TF, and SLAM time-consistency concerns → Simulation timestamps differ from wall time; extra joint-state or transform publishers can create conflicting sources → Use simulation time for model/sensors/controllers/SLAM, retain the Gazebo joint-state source, and audit actual TF publisher identities → Count actual transforms, not just DDS endpoints; the SLAM interactive tools expose another TF endpoint without necessarily duplicating map-to-odom. |
| LiDAR frame and SLAM chain | Scanner self-intersection or frame mismatch can invalidate a visually plausible map → Sensor pose/frame must match the scan plane and complete map–odom–base–scan transform chain → Define a fixed scan frame 0.02 m above the LiDAR visual and verify scan timestamps/TF/map output together → A visible map is only one part of mapping acceptance. |
| Front camera placement | The initial camera placeholder was on a rear feature; the author clarified that feature was a battery enclosure → CAD feature interpretation was wrong → Move the camera to the front centre, keep the original optical-frame convention, and verify image content and calibration topic → Ask about physical intent before changing unrelated geometry. Camera placement is approximate, not a physical calibration. |
| USB input / deadman | Generic button assumptions were unsafe; calibration also waited when joy_node had stopped → The actual `/joy` mapping must be measured; no messages and non-neutral controls are different conditions → Record labelled axis/button samples, require L enable, add B stop/deadzone/wall-time timeout and neutral rearming → Never infer a controller layout solely from its branding. |
| SDL device name | Opening by a displayed device name failed → The enumerate table replaced a comma with a space; raw SDL name retained the comma → Read the exact raw SDL device name and use it in YAML → Human-friendly enumeration output is not always an exact identifier. |
| Keyboard startup readiness | An isolated run timed out waiting for terminal readiness → The keyboard previously allowed only a fixed one-second DDS discovery window; delayed discovery is a plausible cause, though that failed run's terminal output was not retained → Wait conditionally for a subscriber for up to five seconds and include terminal diagnostics on test startup failure → Bound readiness waits by observable state; do not infer that a fixed delay guarantees discovery. |
| Input coexistence | Multiple continuous `/cmd_vel` publishers can overwrite each other → Topic publication is not input arbitration → One router accepts keyboard events and joy input, clears stale keyboard intent and sends output through the original guard → Idle inputs should not continuously publish zeros that suppress another intended source. |
| GUI session ownership | A stale PID file could refer to a different process → PID reuse and independent ROS sessions make global process killing unsafe → Verify user, command, working directory, process group and start time before stopping a recorded session → GUI lifecycle management must not become a second controller or a global `pkill` wrapper. |

## Boundaries

The fixes were accepted for this course simulation. No general-purpose navigation, collision avoidance, IMU gesture control, physical grasping or hardware safety certification follows from these results. Original local diagnostic history stays outside the public release; selected numeric evidence is retained with source-file hashes.
