# 项目事实材料

用途：供作者复核技术事实、准备面试材料。本文件不是最终简历，不把仿真数据包装成真实机器人性能。

## 技术栈与系统组成

- SolidWorks 自建 CAD，10 个 STL；模块化 Xacro/URDF、装配网格偏移补偿、惯性与简化碰撞几何。
- Ubuntu 22.04、ROS 2 Humble、Python 3.10、Gazebo Fortress、RViz 2。
- 四轮 skid-steer：Fortress DiffDrive；ROS Twist 经桥接与现实时间看门狗进入仿真。
- J1–J4：JointTrajectoryController + position 接口；平行夹爪：JointTrajectoryController + effort/PID 接口，两个 jaw 同目标、分别校验实际状态。
- 仿真 LiDAR、RGB camera、odom、joint_states、clock 和 TF；SLAM Toolbox 在线异步建图、地图保存和重新读取校验。
- 键盘与真实 USB Nintendo Pro Controller 输入；实测 mapping、deadman、deadzone、停止与超时；Tkinter 可选启动面板。
- 只读健康检查、隔离 ROS 集成测试、输入/进程归属单元测试和 JSON 证据。

## 五个值得讲的工程难点

1. **CAD 装配坐标与机器人关节坐标分离。** STL 带装配偏移，不能把网格原点直接当转轴。通过 mesh origin 补偿外观坐标，joint origin 定义机构关系；只对毫米网格做 0.001 单位换算。追问：为什么不能简单移动所有 mesh 到原点？惯性和碰撞体的坐标系如何处理？
2. **四轮 skid-steer 接触参数与验证方法。** 转向需要轮地侧向滑动；摩擦方向取决于 collision 局部轴。使用经验证的各向异性摩擦和 slip，并对照物理底盘位姿、轮式 odom。追问：为什么轮子转了而车可能转不动？mu/mu2 与 fdir1 分别控制什么？为何不是通用轮胎模型？
3. **夹爪限位恢复与离散力控制稳定性。** 位置接口在下限附近出现无法恢复运动的现象；切换为 effort/PID 跟踪，保留限位，并把最终控制更新率设为 500 Hz。双 jaw 发送同一目标且分别验证。追问：trajectory controller 与 command interface 有什么区别？为什么只改 PID 而不看更新率可能无效？上游故障原因是否真正证明？
4. **传感器、仿真时间与 SLAM 的一致性。** 排查渲染后端对 LiDAR 的影响，明确 optical/scan frame，验证 map→odom→base→scan 的时间与单一实际发布源。追问：URDF、Gazebo、robot_state_publisher 各负责什么？SLAM 为什么需要 odom？TF 多个 DDS endpoint 是否一定重复发布？
5. **真实输入与安全链的工程化。** 根据真实 `/joy` 采样生成映射；L deadman、B stop、死区、现实时间超时、重新使能；键盘/手柄由单一 router 仲裁，再交给原 guard。GUI 仅复用接口，并验证进程归属。追问：为什么暂停仿真也必须能停车？驱动重复旧数据时超时保护的边界是什么？GUI 崩溃为何不应使 CLI 失效？

## 容易被问错或答错的点

- “夹爪为什么不用 trajectory controller 了？”——前提不正确：仍使用 JointTrajectoryController，只把执行命令接口改为 effort，用 PID 跟踪位移目标。
- “地图闭环 0.4 mm 是定位精度吗？”——不是；它是这次 Gazebo 固定路线的物理终点差，SLAM 对物理位姿误差另有指标。
- “看起来慢是否模型缩小了？”——0.001 是毫米转米；0.05 m/s 本来只有 5 cm/s，低 RTF 又拉长了现实时间。
- “有 Stop 按钮是否达到急停安全标准？”——没有；这是仿真软件命令停止与动作取消，没有独立硬件安全回路。
- “是否完成 SLAM + 导航？”——只完成 SLAM 建图与保存，没有导航、路径规划、自动探索或避障执行。
- “代码是否全部自己写？”——不是。应明确 CAD、需求、人工验收和复核由作者承担，ROS 集成/调试/自动化/文档中有 Codex 辅助实现与运行。
